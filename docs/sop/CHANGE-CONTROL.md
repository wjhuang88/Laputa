# Change Control

Use when accepted requirements, an active Story, a published iteration baseline, provider contract, architecture boundary or user-visible interaction changes after implementation/planning has begun.

1. State the requested change and why current scope is insufficient.
2. Identify affected Hard/Soft/Assumption constraints, Stories, ADRs, tests, docs and active iteration scope.
3. If the change contradicts an ADR, update/supersede the ADR before implementing the contradiction.
4. Decide whether to modify the current Story, add a child/follow-up Story, pause/defer current work, or reject the change.
5. Update owning requirement/backlog/iteration records first; derived summaries second.
6. Re-check readiness/dependencies and validation after the change.

Do not broaden implementation merely because the new direction seems reasonable in chat.
